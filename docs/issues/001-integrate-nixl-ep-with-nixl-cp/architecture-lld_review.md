| expert-2 | high | /scrap/cpu-proxy/nixl/docs/issues/001-integrate-nixl-ep-with-nixl-cp/architecture-lld.md:300 | The LLD makes proxy activity a Phase 1 acceptance requirement and rejects debug-log archaeology, but it does not identify an existing deterministic activity signal or explicitly authorize the proxy-internal instrumentation needed to create one. It also says Phase 1 should consume the proxy without changing internals. In the current source, proxy submissions are only observable through NIXL_DEBUG in src/core/device_proxy/proxy_worker.cpp:122-145, while the NIXL_INFO messages in src/core/device_proxy/proxy_runtime.cpp:683-697 only prove runtime creation. As written, implementers can finish build and host wiring yet every HT or elastic LL correctness pass remains inconclusive under the LLD classifier unless they either violate the scope boundary or weaken the evidence rule. Define the exact evidence hook or an explicit scope exception before implementation. |
| expert-2 | medium | /scrap/cpu-proxy/nixl/docs/issues/001-integrate-nixl-ep-with-nixl-cp/architecture-lld.md:175 | The channel sizing contract depends on Buffer.update_memory_buffers(...) carrying a proxy lane ceiling, but the public API and plan still expose that argument as num_experts_per_rank, and the current C++ runtime only stores it as max_experts_per_rank in examples/device/ep/csrc/nixl_ep.cpp:70-94. For HT callers where the real experts-per-rank value is lower than num_sms/2, a valid existing call can under-provision proxyChannelCount and fail later through device enqueue NIXL_ERR_INVALID_PARAM instead of the promised early EP_PROXY_CHANNELS_UNDERPROVISIONED setup failure. Add an explicit proxy lane-ceiling derivation/parameter, or document and enforce the overloaded contract at the Python boundary before relying on it for validation. |
| expert-5 | medium | /scrap/cpu-proxy/nixl/docs/issues/001-integrate-nixl-ep-with-nixl-cp/architecture-lld.md:71 | The LLD defines `nixl_ep_proxy_clear_context()` with no context or owner argument and sequences each `Buffer` publish/clear through the device proxy context symbol. The plan identifies that this is the global `g_nixl_proxy_ctx`, and the live proxy helper writes it with `cudaMemcpyToSymbol`; meanwhile the existing Python-facing `Buffer` API is instantiable without a declared singleton or single-active-buffer contract. If two proxy Buffers are active in one rank process, a later publish can redirect earlier kernels to the wrong agent/proxy memview registry, and either Buffer's teardown can clear the global context while another Buffer still needs it. That can turn same-process lifecycle overlap into wrong-context proxy submissions or stale-context failures against remote memviews. The implementation/tasks should either enforce one active proxy Buffer per CUDA context/process, make publish/clear owner-aware, or otherwise bind kernels to the intended proxy context before accepting this lifecycle as data-safe. |
| expert-6 | medium | ep-integ-plan.md:68 and ep-integ-plan.md:93, checked against src/core/device_proxy/proxy_worker.cpp:64 | The integration plan says the single worker drains all N proxy channels FIFO round-robin, and uses that assumption to justify the M1 ordering and validation behavior. The current worker loop is not round-robin: for each assigned channel it runs `while (tryDequeue(channel, submission))` before moving to the next channel. A hot channel can therefore keep the worker from servicing other EP lanes. HT and elastic LL both issue work across multiple channel IDs, including flag/counter atomics that gate progress, so this scheduler mismatch can cause proxy validation timeouts or severe tail latency even when channel count is correctly provisioned. The Phase 1 design/tasks should either require bounded/fair per-channel polling in the proxy worker or remove the round-robin assumption and define validation limits that account for possible channel starvation. |
| expert-7 | high | /scrap/cpu-proxy/nixl/docs/issues/001-integrate-nixl-ep-with-nixl-cp/architecture-lld.md:357 | The evidence API requires an ep_proxy_evidence_v1 record containing backend selection, and the classifier accepts HT/LL proxy evidence only when backend == proxy, but the design keeps the same nixl_ep module identity for UCX and proxy builds and does not define a runtime API that lets validation query the loaded module's compiled backend. The current pybind surface exposes Buffer, Config, get_low_latency_buffer_size_hint, topk_idx_t, and is_sm90_compiled, but no selected-backend getter. If validation fills backend from build directory names, environment, or run scripts rather than from the loaded extension, a stale or wrong PYTHONPATH/import can produce misleading evidence while satisfying the JSON shape. Add a minimal extension-owned introspection API or generated evidence field sourced from the compile-time backend macro. |
| expert-7 | medium | /scrap/cpu-proxy/nixl/docs/issues/001-integrate-nixl-ep-with-nixl-cp/architecture-lld.md:115 | The proxy lifecycle API says Buffer::update_memory_buffers(...) provides the allocation-time lane ceiling used for required_proxy_channels, while the existing public API and Python wrapper name that argument num_experts_per_rank. The plan then requires N = num_qps_per_rank = max(num_sms/2, num_local_experts), which is not the same concept for HT. This silently overloads an existing public parameter instead of defining an explicit proxy lane-ceiling contract, so ordinary callers can pass a semantically valid experts-per-rank value that under-provisions proxy channels and fails later in device enqueue rather than at the promised setup boundary. Define a named lane-ceiling parameter/derivation, or document and enforce the overloaded contract at the Python/C++ boundary. |
